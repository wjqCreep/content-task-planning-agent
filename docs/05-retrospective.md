## 最难的问题
让「模型决策」与「代码保证」的边界清楚。守卫写得太强，模型只是在走流程；写得太弱，模型一错就破坏预算或状态。当前做法：模型决定降档、重试、停止和检索关键词，代码保证不超支、不越序、不把失败记为成功。首轮真实运行暴露的资料不足问题，是提示词与暴露给模型的信息共同造成的，改提示词后行为改善，但这依赖模型遵守规则 6，代码层没有强制。

## 学到的
- 状态要给模型看「剩余需要」而不只是总价，否则它会在已经花了钱之后用旧估算做判断。
- 失败后的重规划要结合已保留的结果重新估算，这比单纯重试更能体现模型的调整。
- Mock 通过不等于真实模型通过：真实运行里发现了 Mock 没覆盖的行为（凑素材、多余估算）。

## 下一步
1. 对每个用例重复跑真实模型多次，统计动作序列是否稳定。
2. 把「检索为空且换词仍为空」做成代码层的终止条件或明确的状态，而不只靠提示词。
3. 改用原生 tool-use，减少 JSON 解析容错。
4. 区分空检索与失败调用的计费规则。
5. 在 GitHub 仓库中持续维护评估材料，并在需要时补充新的真实模型运行记录。
